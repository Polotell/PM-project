## 2. WBS 分解思路

本组采用“交付物导向分解法（Deliverable-Oriented WBS）”，以“可验证、可移交、可归档”为叶子节点判定标准。
- 一级划分为 4 大成果域：项目管理成果、业务分析成果、技术实现成果、实验总结成果。
- 二级分解对管理类采用“阶段切分”（启动、计划、配置），对业务类采用“功能域切分”（活动管理、报名管理、审核签到、统计导出）。
- 三级分解落到可独立验收的具体产物，例如：信息结构说明、流程说明、页面原型草案、接口示例、测试用例示例等。
该分解方式保证了“做什么（WBS）—何时做（进度）—如何受控（配置）”三类管理信息的对应关系，便于后续执行与检查。

## 4. 配置管理与协作过程

本组将文档类与示例代码类统一纳入版本管理，受控配置项包括 `README.md`、`docs/01~05`、`docs/conflict.md` 以及 `src/`、`test/`、`assets/`。
分支策略为三层结构：
- `main`：受控发布分支，仅保留课程提交可追溯定稿。
- `dev`：日常集成分支，承接成员成果并解决集成问题。
- `feature-<姓名拼音>`：个人工作分支，每位成员至少一条独立提交记录。
协作流程为：`feature-*` 提交 PR 合并到 `dev`，经验证后由项目经理将 `dev` 合并到 `main`。  
提交信息按“类型 + 简述”规范（如 `docs: 补充 WBS 三级条目`），避免无意义提交说明；公共分支禁止未经沟通的强推改写历史，修正内容通过新增提交留痕。

## 5. 冲突解决过程记录

本次冲突在 `docs/conflict.md` 中制造并解决，目标是演示多人并行修改同一行文本时的真实合并流程。
### 5.1 冲突制造过程
1. 成员A在个人分支修改“当前结论”为“本组决定直接合并到 main”，并提交、推送。
2. 成员B在另一个人分支修改同一行“当前结论”为“本组决定先经过 dev 再合并到 main”，并提交、推送。
3. 两个分支先后发起合并请求，在合并到同一目标分支时触发文本冲突。
   
### 5.2 冲突表现与处理
合并界面（或本地合并）出现典型冲突标记：
- `<<<<<<<`（当前分支内容）
- `=======`（分隔线）
- `>>>>>>>`（待合并分支内容）
小组先沟通两种方案的含义，再结合本项目既定分支策略（`feature-* -> dev -> main`）确定最终保留文本为：  
**“当前结论：先经过 dev 再合并到 main”**。
随后删除冲突标记，完成 `add`、`commit`，再次推送并完成合并。

- 已完成一次真实冲突的发现、协商与解决流程；
- 冲突文件保留在仓库中作为过程证据；
- 结论与配置管理文档中的分支策略保持一致。

## 6. 经验与问题

### 6.1 主要经验
1. 先明确项目边界再开展 WBS 分解，能够有效避免任务扩张与返工。  
2. 采用交付物导向 WBS（三级可验收）后，分工与验收标准更清晰。  
3. 先形成 WBS 再编制进度计划，保证“做什么”与“何时做”一一对应。  
4. 使用 `feature-* -> dev -> main` 分支策略，能将集成风险隔离在主线之外。  
5. 统一命名规范、提交说明和角色职责后，协作沟通效率明显提升。  
6. 通过仓库提交历史保留过程证据，便于检查、复盘与课程评阅。  

### 6.2 存在问题
1. 前期对部分需求与范围的理解不完全一致，导致文档出现反复修改。  
2. 计划与总结阶段任务集中在少数成员，阶段性负载不均衡。  
3. 多人并行修改同一文档同一段落时，合并冲突发生概率较高。  
4. 个别提交前未及时同步 `dev`，增加了冲突处理与二次提交成本。  
5. 功能验证和联调介入偏晚，问题更容易在后期集中暴露。  

### 6.3 改进措施
1. 在项目启动阶段增加一次范围与术语统一评审，尽早形成需求基线。  
2. 关键交付物采用“主责人 + 协作人”机制，降低单点风险并均衡工作量。  
3. 固化“提交前先同步 `dev`、再自查、后提交”的协作流程。  
4. 对高频编辑文档实行“章节认领 + 时间窗口”规则，减少并发冲突。  
5. 在每个里程碑结束前增加一次小规模联调与文档一致性检查。  
6. 持续记录“问题—处理—结果”闭环，沉淀可复用的团队协作经验。
