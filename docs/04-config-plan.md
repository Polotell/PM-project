| `src/`、`test/`、`assets/` | 目录及其中文件（本实验可为占位或示例，仍纳入版本管理） |


## 2. 分支策略
- main
- dev
- feature-*
| 分支 | 用途 |
|------|------|
| `main` | **受控发布分支**：仅集成已通过 `dev` 验证的定稿，用于课程提交与检查。总结报告等最终版必须在此分支上可追溯。 |
| `dev` | **日常集成分支**：成员通过 `feature-*` 合并至此，用于联合同步与解决冲突前的集成。 |
| `feature-<成员拼音>` | **个人工作分支**：从最新 `dev` 拉出；每人至少一条独立提交记录，命名示例：`feature-zhangsan`。 |

流程摘要：`feature-*` →（Pull Request 合并）→ `dev` →（定稿后合并）→ `main`。
## 3. 命名约定

**文档与文件**

- `docs` 下文件名与课程模板保持一致，不随意重命名，便于比较与评阅。
- 正文使用 UTF-8（Markdown）。

**分支**

- 功能分支统一为 `feature-` + **提交人姓名拼音全拼**（小写、无空格），与指导书要求的 Git 提交者身份一致。
- 不与 `main`、`dev` 同名创建个人长期分支。

**提交说明（commit message）**

- 推荐格式：`<类型>: <简短中文说明>`。
- 示例：`docs: 完成配置管理方案`、`docs: 补充 WBS 三级条目`、`fix: 解决 conflict.md 合并冲突`。
- 避免无意义说明（如 `update`、`111`）。

**Git 提交者身份**

- 每位成员 `user.name` 为**本人姓名拼音全拼**，`user.email` 为本人常用邮箱；**全实验期间保持不变**，便于核查个人贡献。
## 4. 合并规则
**合并到 `dev`**

- 成员完成本地提交并 `push` 至己方 `feature-*` 后，在 GitHub 创建 **Pull Request**：**base = `dev`**，**compare = 己方分支**。
- **配置管理员（A）**负责审阅与执行合并到 `dev`；合并前确认无敏感信息误传、文档可打开。
- 若多人同时改同一文件，后合并者应在 PR 页面按提示解决冲突，或拉取最新 `dev` 后再推送更新。

**合并到 `main`**

- 仅在以下条件满足后由 **项目经理（C）** 执行：**`dev` 上 01～05、README 与冲突练习已定稿**，且 **`05-summary-report.md` 已由全组确认**。
- 操作：**将 `dev` 合并入 `main`**（本地或 GitHub 均可），并 `push` 远程 `main`。

**发生冲突时**

1. 不得在未沟通的情况下强制推送改写公共分支历史。
2. 由相关成员协商保留内容；在冲突文件中删除 `<<<<<<<`、`=======`、`>>>>>>>` 等标记，保留一致文本后 `add` / `commit`（或于 PR 上完成解决）。
3. **`docs/conflict.md` 的冲突**：按实验要求协商确定最终一句「当前结论」，并在 `05-summary-report.md` 中记录原因、步骤与结果。

## 5. 版本留痕
- **主线留痕**：以 GitHub 仓库的 **commit 历史** 为准；每次合并 `feature` → `dev`、`dev` → `main` 均应在平台上可见。
- **提交记录**：不伪造、不回撤已提交的公共历史以掩盖协作过程；如需修正内容，使用新的提交修正。
- **（可选）标签**：若课程或小组需要阶段性标记，可在重要节点由 **A 或 C** 在 `main` 或 `dev` 上创建轻量标签（如 `v1.0-handin`）；本组若以「最后一次指向 `main` 的合并提交」作为提交点，亦可不打标签，但须在总结报告中写明以何提交为准。
